# M2 — 큐 + 워커 + 결과 반영

**상태**: 완료 · DoD 7/7 통과  **갱신**: 2026-08-06

## 맥락
ML 채점은 초 단위가 아니라 수 초~수십 초가 걸리므로 동기 응답이 불가능하다. 제출 접수와 채점 실행을 큐로 분리하고, 결과가 DB에 반영되는 경로를 완성한다. 큐를 나중에 붙이면 API 계약을 전부 갈아엎게 되므로 API보다 먼저 세운다.

## 할 일
Redis·BullMQ 연결 -> 큐 2종 분리(`judge:fast`, `judge:slow`) -> 워커 컨슈머(동시성 4) -> 제출 상태 전이(`PENDING` → `JUDGING` → `DONE`) -> 결과 영속화 -> 재시도 정책(`IE`만 자동 재시도 2회) -> 큐 대기 순번 조회.

## DoD (완료 게이트)
1. CLI로 제출 20건을 동시에 넣었을 때 전부 `DONE`으로 수렴하고 유실 0건.
2. 워커 동시성이 4를 넘지 않는다 — 동시 실행 컨테이너 수 관측으로 확인.
3. 워커를 채점 도중 강제 종료 후 재기동하면 해당 작업이 재처리되고 중복 결과가 생기지 않는다.
4. `IE` 발생 시 자동 재시도가 동작하고, 재시도 후에도 실패하면 `IE`로 확정된다.
5. `IE` 제출이 정답률·랭킹 집계 쿼리에서 제외된다.
6. 제출 접수부터 채점 시작까지 지연 P95 < 2초 (큐 비적체, 20건 기준).
7. 제출 1건당 컨테이너 1개가 생성·파기된다(INV-8 준수) — 20건 처리 후 잔존 컨테이너 0개.

## 검증
~~~bash
pnpm db:up && pnpm db:migrate            # Postgres·Redis 기동 + 스키마
pnpm dev:worker                          # 워커는 별도 프로세스로 떠 있어야 한다

pnpm bench:submit -- --count 20                    # DoD 1·2·7 (일괄 투입 = 적체)
pnpm bench:submit -- --count 20 --paced            # DoD 6 (큐 비적체)
pnpm bench:submit -- --induce-ie --count 3         # DoD 4·5
# DoD 3 은 벤치 실행 중 워커를 SIGKILL 후 재기동
~~~

생산과 소비를 한 프로세스에서 돌리지 않는 것이 중요하다. 같은 프로세스면 동시성 상한을
자기 자신이 보고하게 되어 관측이 아니라 자백이 된다.

## 증거

깨끗한 DB(`pnpm db:reset`)에서 실행. 워커 동시성 4, 이미지 `mlca-python:3.11`.

### DoD 1·2·7 — 20건 일괄 투입
~~~
수렴        20/20  (11351ms)      유실 0건
판정 분포   {"AC":20}
동시 컨테이너 최대 4  (표본 57회)  ← 동시성 상한을 넘지 않는다
잔존 컨테이너 0                    ← INV-8
~~~
동시 컨테이너는 워커의 자기 보고가 아니라 `docker ps` **외부 관측**이다.

### DoD 6 — 큐 비적체 지연
~~~
큐 지연     P50 6ms  P95 8ms  max 10ms      (게이트 2000ms)
~~~
처음에는 20건을 한꺼번에 넣고 쟀더니 P95 가 8.9초로 나왔다. 그 값은 **앞선 제출을
기다린 시간**이지 채점 시작 지연이 아니다. 동시성 4에 20건이면 큐가 적체되는 것이
당연하고, DoD 가 "큐 비적체"를 명시한 이유가 그것이다. 미완료 건수를 동시성보다
낮게 유지해 다시 쟀다.

### DoD 3 — 채점 도중 워커 강제 종료
~~~
SIGKILL 시점: JUDGING=4  실행중 컨테이너=1
종료 직후 고아 컨테이너: 4
재기동 후:   12/12 AC  최대 시도 2  잔존 컨테이너 0
중복 결과:   solved 중복 0, DONE 인데 verdict 없음 0, JUDGING 갇힘 0
~~~
회수까지 약 70초 걸린다. `stalledInterval` 30초 설정과 일치한다.

### DoD 4 — `IE` 자동 재시도
~~~
판정 분포 {"IE":3}   최대 시도 3   status=DONE
[worker] 실패 job=41 시도=1: 문제 디렉터리를 찾을 수 없다
[worker] 실패 job=41 시도=2: 문제 디렉터리를 찾을 수 없다
~~~
최초 1회 + 자동 재시도 2회 후 `IE` 로 확정된다. `JUDGING` 에 갇힌 제출은 없다.

### DoD 5 — `IE` 집계 제외
~~~
slug             judged accepted excluded rate
ie-missing-cases      0        0        3    -
l2norm               52       52        0  100.0
user_ranking:  bench  solved_count=1
~~~
`IE` 는 분자에도 분모에도 들어가지 않는다. AC 52건인데 `solved` 가 1행인 것은
최초 AC 에만 기록하기 때문이다.

## 이 phase 에서 잡은 버그

**고아 컨테이너 이름 충돌로 제출이 영구 `IE` 가 되는 경로.**
컨테이너 이름은 제출 ID 에서 나오고 재시도는 같은 제출 ID 를 쓴다. 워커가 `docker run`
직후 죽으면 정리 코드가 돌지 못해 컨테이너가 남고, 그 상태로 재시도하면 이름 충돌
(`exit 125 Conflict`)로 생성이 실패한다. 크래시 복구가 오히려 제출을 망가뜨린다.

DoD 3 실측에서 **고아 컨테이너가 실제로 4개 남는 것**을 확인했다. 생성 전에 같은 이름을
먼저 치우도록 고쳤고, `judge-fixtures` 에 회귀 가드를 넣었다(고아를 일부러 만들고
재채점이 `AC` 가 되는지 확인). M1 게이트는 24건 → 25건이 됐다.

## 롤백 계획
큐 이름에 버전 접미사를 두어(`judge:fast:v1`) 스키마 변경 시 새 큐로 전환하고 이전 큐는 드레인만 시킨다.

## 리스크 / 미지수
- 무거운 제출 하나가 큐를 막을 수 있다. Phase 1은 학습 문제가 없어 위험이 낮지만 큐 분리는 미리 해둔다.
  현재 `judge:slow` 는 상수로만 존재하고 아무도 넣지 않는다. 분기 기준은 학습 문제가 생길 때 정한다.
- ~~워커가 죽으면 `JUDGING` 상태로 고아가 남는다.~~ → `stalledInterval` 30초·`maxStalledCount` 2 로
  회수된다. 실측 회수 시간 약 70초.
- **채점 1건당 약 2초가 컨테이너 왕복 비용이다.** 실제 풀이 시간은 1ms 미만인데 `docker run`·
  `wait`·`inspect`·`logs`·`rm` 다섯 번의 프로세스 기동이 대부분을 차지한다. 동시성 4 기준
  시간당 약 7,200건으로 §12 의 목표 2,800건을 넘으므로 지금은 문제가 아니다. 병목이 되면
  attach 모드로 `wait`·`logs` 를 합쳐 다섯 번을 세 번으로 줄일 수 있다.
- BullMQ 의 stalled 회수가 `attempts` 를 소비한다. 워커가 두 번 죽으면 정상 제출이
  재시도 한도에 걸릴 수 있다. 실측에서는 최대 시도 2로 여유가 있었다.
- 마이그레이션 러너에 advisory lock 이 없다(ADR-0008). 단일 호스트·수동 배포 전제이며
  M7 에서 배포 절차를 정할 때 재검토한다.

## 주의
재시도는 `IE`에만 적용한다. `WA`·`TLE`를 재시도하면 사용자 코드가 여러 번 실행되어 자원이 낭비되고 통계가 오염된다.
