# ADR-0007: 채점 워커를 컨테이너가 아니라 호스트 프로세스로 운용한다

- **상태**: 채택
- **일시**: 2026-08-07
- **관련**: M1, M2, M7, `deploy/README.md`, INV-4·INV-8

## 맥락

워커는 제출 1건마다 격리 컨테이너를 만들고 지운다. 그러려면 Docker 소켓에 닿아야 한다.
M1 부터 "소켓 마운트는 사실상 호스트 루트 권한"이라는 위험을 열어 둔 채로 왔고, M7 의
배포 구성이 이 결정을 더 미룰 수 없게 했다.

선택지는 셋이었다.

1. 워커를 호스트 프로세스로 두고 `docker` 그룹 소속으로 소켓에 접근
2. 워커도 컨테이너로 올리고 `/var/run/docker.sock` 을 마운트
3. rootless Docker 로 전환

## 결정

**1번.** `api`·`postgres`·`redis`·프록시는 compose 로 올리고, 워커만 systemd 유닛으로
호스트에서 돈다 (`deploy/mlca-worker.service`).

## 근거

- **검증한 형태와 배포하는 형태를 같게 둔다.** M1~M6 의 격리 게이트 25건이 전부
  "워커는 호스트 프로세스, 채점 대상만 컨테이너" 상태에서 통과했다. 2번으로 옮기면
  한 번도 게이트를 통과한 적 없는 형태로 배포하게 된다. 이 프로젝트에서 가장 비싼
  실수는 "돌기는 하는데 검증된 적 없는 구성"이다.
- **2번에는 조용한 함정이 있다.** 워커가 `-v <경로>:/judge` 를 지정하면 그 경로는
  **호스트 데몬이 해석한다** — 워커 컨테이너 안의 경로가 아니다. 작업 디렉터리를
  호스트와 동일한 절대경로로 bind mount 하지 않으면 채점이 빈 디렉터리를 읽고,
  증상은 전 제출 `IE` 또는 케이스 0건 통과다. 맞출 수는 있으나 틀리기 쉽고,
  틀렸을 때 원인이 멀다.
- **3번은 지금 검증할 수 없다.** 개발 환경이 Windows + Docker Desktop 이라 rootless
  데몬을 세울 수 없고, 검증할 리눅스 호스트도 아직 없다. rootless 에서
  `--pids-limit`·`--memory` 가 실제로 걸리려면 cgroup v2 delegation 이 필요하며,
  안 걸리면 INV-4 격리 전제가 깨진 채로 돈다. **확인 없이 옮기는 것이 가장 나쁘다.**
- 1번은 소켓을 컨테이너 안에 두지 않으므로 노출면이 2번보다 작고, 3번으로 가는 길을
  막지 않는다 — 데몬만 바꾸면 워커 코드는 그대로다.

## 결과 / 트레이드오프

- **이득**: 검증된 형태 그대로 배포. 볼륨 경로 해석이 자연스럽다. rootless 이행 경로가 열려 있다.
- **비용**: 기동이 `docker compose up` 하나로 끝나지 않는다. compose + systemd 두 갈래이며
  배포 문서가 그만큼 길어진다 (`docs/ENVIRONMENT.md` §7).
- **남은 위험 (숨기지 않는다)**: `docker` 그룹 소속은 여전히 호스트 루트 등가다.
  줄인 것은 노출면이지 권한이 아니다.

## 위험을 받치는 것

권한 자체를 없애지 못하므로 두 겹으로 받친다.

1. **워커는 사용자 코드를 실행하지 않는다.** 큐에서 제출 ID 를 꺼내 컨테이너를 만들고
   결과를 DB 에 쓸 뿐이다. 이 명제가 깨지면 임의 제출이 곧 호스트 루트가 되므로,
   문서가 아니라 검사로 고정했다 — `apps/worker/src/architecture.test.js` 가
   프로세스 생성 지점이 하나인지, `eval`·`vm` 경로가 없는지, 제출 원문을 적재하는
   코드가 없는지를 본다.
2. **systemd 유닛으로 파일시스템·커널 인터페이스를 잠근다.** `ProtectSystem=strict`,
   `CapabilityBoundingSet=`(비움), `NoNewPrivileges`, `SystemCallFilter=@system-service`.
   쓸 수 있는 곳은 제출 작업 디렉터리 하나다.

## 재검토 조건

리눅스 호스트를 확보하면 rootless Docker 를 시험한다. 판정 기준은 `pnpm judge:fixtures`
25건이 rootless 데몬에서 그대로 통과하는지 하나다 — 특히 pids-limit 과 메모리 상한.
통과하면 3번으로 옮기고 이 ADR 을 대체한다. 통과하지 못하면 옮기지 않는다.

## 검토한 대안

- **워커 전용 호스트로 분리** — 소켓 침해가 API·DB 와 같은 기계에 닿지 않는다. Phase 1 은
  단일 노드 전제(`docs/TECHNICAL.md` §12)이고 노드를 늘리면 그 전제가 깨진다. 트래픽이
  단일 노드를 넘길 때 워커 수평 확장과 함께 다시 본다.
- **소켓 프록시(tecnativa/docker-socket-proxy 등)로 API 표면 제한** — 2번의 위험을
  줄이는 방법이지만 2번을 전제한다. 1번을 고른 이상 얹을 대상이 없다.
