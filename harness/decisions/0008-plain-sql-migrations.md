# ADR-0008: 마이그레이션을 평문 SQL 파일 + 최소 러너로 관리한다

- **상태**: 채택
- **일시**: 2026-08-06
- **관련**: M2, M3, `docs/TECHNICAL.md` §6

> 번호가 0007 을 건너뛴다. 0007 은 Docker rootless 운용 결정의 후보 번호로 여러 문서가
> 이미 참조하고 있어 비워 둔다.

## 맥락
M3 의 DoR 이 "마이그레이션 도구 결정"을 M3 시점으로 잡았으나, M2 가 채점 결과를 영속화하려면
그 전에 스키마가 있어야 한다. 결정을 앞당긴다.

선택지는 마이그레이션 라이브러리(node-pg-migrate, Umzug 등)와 평문 SQL + 자체 러너다.

## 결정
`migrations/NNNN_name.up.sql` / `.down.sql` 쌍을 두고 `tools/migrate.js` 가 적용한다.
적용 이력은 `_migrations` 테이블에 남기고, 각 마이그레이션은 단일 트랜잭션으로 실행한다.

## 근거
- 백서 §6.1 이 이미 **완성된 DDL** 이다. 라이브러리의 DSL 로 옮기면 백서와 코드가
  서로 다른 언어로 같은 것을 두 번 말하게 되고, 대조가 어려워진다. 평문 SQL 은 백서를
  그대로 옮긴 것이라 눈으로 대조된다.
- Phase 1 의 스키마는 테이블 9개로 고정돼 있고 자주 바뀌지 않는다. 라이브러리가 제공하는
  자동 생성·스키마 diff·다중 방언 지원 중 필요한 것이 없다.
- 러너가 하는 일은 "정렬해서 순서대로, 트랜잭션 안에서, 이력 기록"뿐이다. 이 정도를
  의존성으로 들이면 그 의존성의 업그레이드가 스키마 변경의 리스크가 된다.
- `pg` 는 어차피 필요하다. 추가 의존성이 0 이다.

## 결과 / 트레이드오프
- 이득: 백서와 1:1 대조 가능, 의존성 없음, 롤백이 명시적(`down.sql` 을 반드시 쓰게 된다).
- 비용: 러너를 직접 유지한다(약 100줄). 라이브러리가 주는 잠금(advisory lock)·병렬 안전성을
  직접 챙겨야 한다 — Phase 1 은 단일 호스트·수동 배포이므로 지금은 문제가 아니다.
- 한계: 여러 인스턴스가 동시에 마이그레이션을 돌리는 상황은 상정하지 않는다. M7 에서
  배포 절차를 정할 때 advisory lock 을 추가할지 결정한다.

## 검토한 대안
- **node-pg-migrate** — 성숙하고 잠금도 제공하나, DDL 을 JS DSL 로 다시 쓰게 되어 백서 대조가
  깨진다. `--sql-file` 모드로 평문 SQL 을 쓸 수도 있지만 그러면 러너만 남고 이득이 사라진다. 기각.
- **Prisma/Drizzle 등 ORM 마이그레이션** — 스키마 소스가 ORM 모델로 옮겨간다. 백서가 원본이라는
  전제와 충돌하고, JSONB·부분 인덱스·CHECK 제약을 표현하려면 결국 raw SQL 로 내려간다. 기각.
