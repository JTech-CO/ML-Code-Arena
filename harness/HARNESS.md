# HARNESS.md — 마스터 운영 매뉴얼

> "무엇을 만드는가"(백서)가 아니라 **"어떻게 진행·검증·복구하는가"(운영 규율)**. phase의 "완료"는 코드가 도는 것이 아니라 **측정 가능한 게이트(DoD) 통과**다. 게이트로 막지 않으면 잘못된 완료 판정이 다음 phase로 전파된다.

## 0. 세션 루프
1. 시작: `PROGRESS.md` → 현재 phase·다음 할 일·미결 → 해당 `phases/Mn.md` + 관련 `docs/` 절.
2. 작업: 한 번에 한 phase. 작업 단위마다 그 phase의 검증 명령으로 게이트 확인.
3. 종료: `PROGRESS.md` 갱신(완료 체크·증거·다음 할 일·새 미결·결정 링크) → 커밋.

### 0.1 완료 판정
DoD 항목이 **전부** 충족되어야 완료. 하나라도 미달이면 미완료로 두고 다음 phase로 가지 않는다.

### 0.2 의존 순서
M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7.

M1(채점 러너)이 전체의 계약 원점이다. M1의 판정 코드·러너 출력 스키마가 확정되기 전에 M3(API)이나 M5(프론트엔드)를 진행하면 스키마를 다시 짜게 된다. M4(디자인 토큰)는 M5 이전이면 언제든 가능하지만, 토큰이 흔들리면 컴포넌트를 전부 다시 손대므로 M5 직전에 확정한다.

### 0.3 증거 기반 완료
게이트 "통과"를 주장할 때, 근거가 되는 **명령과 핵심 출력**(테스트 요약·수치·로그 일부)을 해당 `phases/Mn.md`의 증거 칸과 `PROGRESS.md`에 남긴다. 증거 없는 완료 주장은 미완료로 본다.

채점 관련 게이트는 **판정 코드 8종이 전부 재현되는 것**을 증거로 삼는다. `AC`만 나오는 상태는 채점기가 동작한다는 증거가 아니다.

## 1. 파일 라우팅

## 2. 멈춤 규칙 (STOP)
### 2.1 멈춰야 하는 상황
- 같은 에러/실패를 서로 다른 방법으로 **3회** 시도해도 미해결.
- DoD 게이트(특히 불변식·핵심 기능 실효·정합성)를 못 넘는데 우회 충동.
- 불변식(`INVARIANTS.md`)을 깨야만 통과 가능.
- 큰 아키텍처 변경 필요 추정.
- 외부 제약(필요 자원 없음·대상 접근 불가·약관/정책 위반 소지).
- **격리 옵션을 완화해야 채점이 되는 상황.** 이것은 설정 문제가 아니라 설계 문제일 가능성이 높다.

### 2.2 멈출 때 절차
1. `PROGRESS.md`에 기록: 증상 / 재현 방법 / 시도한 것들 / 가설 / 막힌 지점.
2. 사용자에게 요약 보고, 선택지가 있으면 제시한 뒤 결정 요청.
3. 결정 전까지 불변식을 깨는 임시 우회를 만들지 않는다.

### 2.3 절대 금지 (레드라인)
`CLAUDE.md`의 레드라인과 동일.

## 3. 검증 우선순위 (한 줄)
격리·비노출 불변식 > 채점 정확성 > 핵심 기능 실효 > 통합 정합성 > UX/배포.

일반 프로젝트는 "불변식/규칙 정확성"이 최상위지만, 이 프로젝트는 그 앞에 **격리**가 온다. 채점이 정확해도 격리가 깨지면 서비스를 열 수 없다.

## 4. 채점 관련 작업 규율 (이 프로젝트 고유)
1. 러너(`judge/runner/`)를 수정하면 **판정 8종 재현 테스트를 반드시 다시 돌린다.** 러너는 모든 판정의 단일 출처다.
2. 문제 정의를 추가·수정하면 **기대값을 `reference.py`로 재생성**한다(INV-10). 손으로 고치지 않는다.
3. 격리 옵션(`docker run` 플래그)은 **단일 상수 모듈 한 곳**에만 둔다. 여러 곳에 흩어지면 하나를 놓친다.
4. 새 판정 코드를 추가하려면 러너·DB enum·API 응답·`VerdictLabel`·카피 5곳을 동시에 고친다. 하나라도 빠지면 UI에 빈 칸이 뜬다.
